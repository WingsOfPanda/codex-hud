# Codex Plus 0.163.0-plus.0.4.2

This note describes the source changes and release requirements. Qualified
archive identities and per-target results belong to the matching release
handoff; this source note alone does not establish package qualification.

## Scope

This patch refines the native status footer, worker role prefixes and distinct
status item colors, places the Plus goal row above editable input in blue, and
repairs readiness checks when an exact admitted turn is not yet visible in
history. It retains the stock daemon, detached jobs and Ultracode.
See the [current release notes](../release-notes.md) for behavior details.

Upstream remains official Codex 0.163.0, commit
`83086188ae0614bd882818ff1aa23f3194962012`. Rust is 1.99.1, coordinator protocol
is 5 and execution-record format is 1. Voice and the Python runtime remain
omitted. Historical release notes and handoffs are unchanged.

## Qualification requirements

Freeze the final Plus source commit after UI acceptance, then build and qualify
complete archives from that identical commit on native x86_64 and aarch64 hosts.
Each package manifest's `plus_commit` must match that frozen source; the final
handoff must match the qualified manifests and archive digests.

Required evidence before qualification:

- Focused native Rust HUD/status/goal tests, terminal smoke and clean patch
  application for the changed frontend; exact-turn admission regression checks.
- Complete extracted-package acceptance on each native architecture, including
  runtime/lifecycle/stock-daemon gates, launch/resource discovery and package,
  manifest, mode, tree and archive validation.
- Actual 0.4.1/0.4.2 helpers and immutable package copies for forward/quiet
  rollback, admission/steering snapshots, maintenance holds, settled ledger and
  execution records, one workload side effect and no replay.
- Actual 0.4.0/0.4.2 helpers for continued shared-ledger input and steering
  before TUI restart. This does not promote 0.4.0 to a rollback target.
- Pane captures with a Plus goal, both status rows, a full activity strip and
  shortcut/history hints: at most five nonempty rows below the prompt. Preserve
  the exact fleet status selection and color setting through load/save.
- Exact source, toolchain and package identities, executed checks, failures,
  skipped checks and host limitations for each target. Record whether concurrent
  old/new native TUI operation was tested; do not infer it from helper checks.

Local metadata/source-guard checks are preparation evidence only. Prior feature
acceptance, reused historical results and unchanged protocol/format identities
cannot qualify these final complete packages.

## Fleet contract

Use `quiet_checkpoint: true`, `executions: wait`, `daemon_restart: false` and
`session_restart: required` to obtain the new frontend. Mixed-version correctness
remains subject to the actual qualification above. Keep qualified 0.4.1 as the
rollback floor and retain every package referenced by a process or unresolved
execution. No live running-executor rollback is claimed. Preserve disabled native
goals, the ledger and existing global AGENTS instructions (`agents_md: null`).

The intended `retain` list is `["0.163.0-plus.0.4.1"]`. Thus 0.4.0 stops being
retained as a floor and becomes removable once unused; in-use package retention
still applies. The matching final handoff must certify native quiet rollback
over 0.4.2-written records before calling 0.4.1 qualified.

No new config key is introduced. Both `tui.status_line` and
`tui.status_line_use_colors` accept the existing fleet values unchanged. The
existing upstream `tui.screen_reader_detection_done` may still be written on
first launch in a fresh home; that behavior predates this release.

Publication, fleet staging/test and deployment require their own authorization.
Populate handoff hashes only from verified native manifests and archives, using
the [handoff procedure](../releasing.md#qualification-and-handoff).
