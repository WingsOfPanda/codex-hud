## Qualification and limits

Source acceptance passed 35 Rust HUD tests, nine terminal-fixture checks, clean
and reverse patch application, and 12 packaging tests. Each extracted optimized
package passed all 18 terminal stages, eight shell-policy cases, independent-pane
and process-cancellation checks, CLI/stdio Code Mode, wrapper routing with stubs,
and park/wake through an official stock daemon with exactly one callback.
Runtime checks preserved package manifests and official binaries. HUD refresh
added no model turns; provider fixtures stayed on loopback.

Primary acceptance independently verified both exact archives, wrapper routing
with stubs, all 18 terminal stages, and unchanged extracted package inventories
on their native hosts. ARM's archive remained on 910b throughout these checks.

The raw package gate retains **8/9 passing checks and exit 1** on both targets:
direct bundled bwrap cannot set up its UID map under the host policy. The official
helper fails identically. Separate supported CLI sandbox tests pass for stock
and Plus, including read-only enforcement. This is the existing **host policy,
same as stock, unused by the configured fleet** limitation; no security setting
was changed. The CLI's chosen sandbox helper path was not traced.

Initial harness failures are retained: x86 used a Python without pyte before the
full suite passed in the existing fixture environment; the ARM evidence-summary
guard expected different wording for the known bwrap failure before correction.
Neither correction changed the qualified package bytes.

ARM Rust/Cargo homes, caches, temporary files, sources, outputs, and private test
homes stayed under `/data`. X86 reused the existing Cargo cache, including normal
cache bookkeeping writes; Rustup configuration/defaults were unchanged. Installed
Plus packages, wrappers, shared daemon, and global configuration were unchanged.

The full upstream suite, older glibc versions, and actual four-box rollout were
not tested. Glibc 2.39 is the tested baseline, not a measured minimum version.

## Update and rollback

Publication, merge, and rollout remain separate user gates. Fleet-config owns
pins, wrappers, installed-package checks, and the update. Existing sessions need
relaunching after rollout; the build alone does not change their display. Rollback
to plus.2 keeps the same upstream CLI/daemon version; preserve packages still used
by running processes. No global park/shell instruction change is needed.
