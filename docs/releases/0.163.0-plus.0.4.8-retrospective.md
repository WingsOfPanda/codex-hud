# 0.4.8 release retrospective

Read-only review, 2026-10-24. All times below are UTC on 2026-10-23. Paths beginning `R/` identify privately retained workspace evidence under `.build/release048/`. `E/<UUID>` identifies the coordinator root’s managed execution directory under `$CODEX_HOME/codex-plus/executions/v1/`. These are historical locators, not portable public proof; the [published qualification](0.163.0-plus.0.4.8/qualification.json) and committed native logs/captures provide the final portable evidence. Original outcomes and frozen source/tooling were not modified. The [timing extraction](0.163.0-plus.0.4.8-retrospective-timings.json) preserves the measured intervals.

Most recorded failures were qualification fixture, environment or provenance errors; their share of the elapsed release window is not measured. The largest gap also contains user-requested recovery-runtime implementation, whose duration was not isolated. These should not be described collectively as x86/ARM product failures. The final native packages, compatibility and AP results were accepted. Some stops were necessary because cleanup identity or provenance was uncertain; the avoidable part was discovering ordinary fixture/profile mismatches only after expensive native work and repeatedly changing the qualification plan.

## What a smooth next release can retain

Prepare both actual host profiles first; complete the migrated semantic fixture checks and the full producer-shaped evidence-consumer chain before native launch. Keep frozen source/tooling immutable, including Git metadata, and state explicitly which checks require the real profile interpreter and fixture sites. Treat provenance, cleanups and immutable result identities as gates; use independent evidence plus a committed coordinator-only verifier repair when that fully solves a consumer mismatch. Continue already-authorized scoped recovery where policy permits; only a concrete missing authority, unknown ownership, immutable-record conflict or changed execution plan should block its dependent step.

Final completion evidence is `R/preparation-v5/x86-final-acceptance.json`, `R/preparation-v5/arm-final-acceptance.json`, returned native/compat receipts and `R/publication-final/publication-verification.json`. They record 418 native tests per architecture, compatibility/captures, AP and five published assets. This read-only review checked preserved records, not a fresh build, execution, remote host, installed fleet or download verification. It intentionally did not replay failures, mutate sealed checkouts, clean processes, or estimate undocumented approval delays.

## Changes after the retrospective

The updated release book assigns one continuous native-owner brief through compatibility and export, requires owners to record future-phase prerequisite checks before expensive work (the whole table is not enforced by one CLI), separates stable readiness from near-launch baselines, and distinguishes ordinary local review from missing user authority. Documentation now points at the published0.4.8 proof instead of declaring that release pending.

One additional verifier inconsistency was found by code review: the AP receipt adapter still compared saved/raw results exactly, bypassing the shared finite adjacent-float timestamp matcher. A narrow fix and regression preserve original bytes, accept the already-supported adjacent timestamp case, and reject other differences. Root acceptance passed **51 adapter/protocol tests** (12 adapter, 39 protocol), managed log `6f523a52-5575-4d67-8c26-c3c390394d56`. The implementation is commit `e50e1e6`, integrated as `927ca20`; it is a follow-up tooling change, not a modification to the published 0.4.8 tag. Advisor reviewed the draft with Opus5.5/xhigh and returned revise; the [finding dispositions](0.163.0-plus.0.4.8-retrospective/advisor-dispositions.json) record the root’s corrections and verification. No second Advisor approval is claimed.

No fresh native build, hardware/concurrency experiment or end-to-end unattended release has been run for this retrospective. Cross-attempt native receipt reuse and a one-command release orchestrator remain unimplemented; the book does not claim them.

## Native-owner corroboration and additions

The [ARM owner's report](0.163.0-plus.0.4.8-retrospective/postmortem.md)
was received with SHA256 `513397fa2bac100999204daf0ad58b4c1946582cd3f21d6941fe3bfd06d9b8f5`.
Its independently supplied bundle hash was
`bf2ac7f9f02bdbabb0fd8d0ae466c7fe31d003d0449d053c001d2b293c117253`.
Both transferred hashes matched. The owner rechecked 54 source files' hashes,
modes and mtimes; no original evidence changed. Its memory search was unavailable,
so findings use preserved files and a bounded transcript prefix.

- Six ARM preparation directories meant **three full native executions**;
  the other three refused/unlaunched preparations did not compile.
- An unfiltered offline Cargo metadata query requested Windows-only dependencies.
  Filtering to the native target resolved the actual ARM graph without a download.
- The v3 package stage itself failed on EXDEV even though an archive existed.
  The generic “Stage produced no report” fallback obscured the first fixture error;
  native tests were never reached. A future failed-stage reporting improvement
  must retain the raw subgate/error path, not promote the archive to acceptance.
- A paired nonzero guard exit was classified as an incomplete journal by the old
  conservative validator. Terminal failure and missing terminal evidence are
  distinct facts. The existing recovery path still needs exact physical proof;
  changing that validator's policy requires its own tests and qualification.
- The owner's private review briefly used sorted serialized closure keys instead
  of the original proposal order for numeric input snapshots. It also compared
  integer tar mode 256 with string `"0400"`. These were reviewer errors,
  corrected against the existing artifacts without another prepare/export.
- The interval from native proof return to compatibility authorization was
  **25m48.618s**, including archive transfer/root acceptance. The subsequent
  **15m54.298s** to the actual compatibility start was local preparation and
  review, not another permission wait. Neither interval is pure idle time.
- Stale relay snapshots arrived after launch or completion. Exact UUID/state
  receipts prevented duplicate launches; acknowledgement is not a phase gate.
- Existing Cargo caches still reported 153 compiled/1157 fresh frontend artifacts
  in both v4/v5, with different upstream workspace paths. This supports investigating
  freshness, not claiming a proven cause or automatic byte-identical binary reuse.

The [owner's proposed brief](0.163.0-plus.0.4.8-retrospective/native-owner-brief.md)
is historical input, not an execution grant. The current book resolves its
coordination tradeoff by freezing both stable profiles first and allocating
volatile baselines near local launch; it explicitly delegates or reserves local
package approval. It does not require an archive-transfer acknowledgement before
already-authorized local compatibility. The final publication gate stays with
the coordinator.

Root-only finalization traceback checks additionally confirmed the pinned-Python
error (`ea220517`), ignored-reasons type error (`677081e2`), partial-transfer
hash assertion (`15dd65f0`) and immutable-ready-record permission error
(`c14b85fa`). These are orchestration errors, not candidate failures.
