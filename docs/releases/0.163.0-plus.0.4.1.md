# Codex Plus 0.163.0-plus.0.4.1

This helper-only patch fixes transient first-turn admission warnings and hidden
Ultracode confirmation failures. It retains the official Codex 0.163.0 daemon
and the unchanged frontend from 0.4.0.

## Changes

- Retry only the exact temporary unsupported turn/item history errors: four
  total read attempts, with 100 ms between attempts, on the same connection.
- Require positive evidence for the exact turn and initial user message. Never
  resend accepted input or infer admission from requested mode settings.
- Show `Ultracode unavailable` with a reason if mode confirmation still fails.
  A later `/ultracode status` can recover once history is readable. Accepted
  user input stays accepted; confirmed modes survive steering unchanged.

Frozen Plus source: `727163057a18aa17ff9cd539ae2af2440b6e890d`. Upstream:
`83086188ae0614bd882818ff1aa23f3194962012`. Rust 1.99.1, GNU targets, glibc 2.39,
coordinator protocol 5 and execution-record format 1. Voice and Python runtime
are omitted. No shared-daemon change or new ledger migration is introduced.

## Native qualification

Both complete archives were assembled from the same frozen source and tested
after extraction on their native x86_64 and aarch64 hosts. Each passed:

- 183 Rust runtime tests and 29 black-box coordinator tests, including all 12
  admission regression cases.
- 16 runner tests (3 explicit Python-only implementation skips), 7 upgrade
  tests, stock integration, and all 6 stock lifecycle scenarios.
- Official-daemon Ultracode admission, observer recovery and compaction checks;
  4 terminal cases including unavailable/recovered mode; 23 terminal smoke stages.
- Fresh-home operator routing/JSON probes and final package, manifest, file-mode,
  tree, archive and immutable-source checks.

x86 also passed all 32 custom-goal scenarios; ARM reran input-epoch and
pending-input-before-turn and inherits the unchanged remaining scenarios from
0.4.0. ARM passed all 9 package gates. The x86 raw bwrap UID-map probe is denied
by host policy identically for official and Plus; both CLI read-only sandbox
checks passed. That limitation was retained, not bypassed.

The frontend, Code Mode host and bwrap binaries are reused byte-for-byte from
qualified 0.4.0 after verifying original provenance and hashes. Unchanged
frontend Rust/HUD, additional detached/advisor, dedicated SSH lifetime and
bootstrap pressure suites were not rerun. Full upstream tests and real-provider
benchmarks were not run. The original timing race remains unconfirmed; its
exact RPC failures are reproduced by focused fault injection.

## Fleet compatibility

Native tests on both architectures used the actual 0.4.0 and 0.4.1 helpers,
complete immutable package copies, a private official daemon and loopback
providers. They verified quiet rollback over 0.4.1-written ledger/execution
records, unchanged SQLite schema and every settled row, unchanged execution
result, one workload side effect, and no replay. Maintenance holds were entered,
read and left across versions in both directions with matching hold identities.
Alternating old/new helpers preserved exact admission and steering snapshots.

The first compatibility attempts exposed a test-harness error: it held the
supervisor lock while expecting an automatic completion callback. The corrected
gate passed on both architectures with all assertions retained; package bytes
were unchanged. [Verification summary](https://github.com/WingsOfPanda/codex-plus/blob/0.163.0-plus.0.4.1/docs/releases/0.163.0-plus.0.4.1/verification.json) and the
[repeatable gate](https://github.com/WingsOfPanda/codex-plus/blob/0.163.0-plus.0.4.1/docs/releases/0.163.0-plus.0.4.1/verify-compatibility.py) record the scope and evidence.

Use a quiet checkpoint with `executions: wait`; enter maintenance with the current
helper, perform fleet quiet/install checks, then leave using the selected helper.
Keep 0.4.0 as previous and rollback floor, plus every package still named by a
process or unresolved execution. No running-executor rollback or live observer
downgrade is qualified here.

Restarting a 0.4.0 TUI is optional for compatibility and recommended to load the
adjacent-helper fixes. Mixed 0.4.0/0.4.1 helper operation was tested; simultaneous
native TUI instances were not. Legacy 0.3.x adjacent helpers remain unqualified
against protocol-5 state: restart those sessions before further Plus operations.
Retention alone does not qualify a rollback below 0.4.0.

Fresh-home probes are unchanged: `job list --all` returns exactly
`{"schema":1,"execution_record_format":1,"unresolved":[],"packages":[]}`;
`ultracode status` reports unavailable/off, null effective/load, and empty pending.
Its existing journal-directory and unavailable-reason fields remain present.
There is no daemon restart or AGENTS block change. Fleet staging/test, main merge
and deployment remain separate approvals.
